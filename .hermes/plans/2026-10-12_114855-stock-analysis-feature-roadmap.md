# 股票分析页数据能力扩展方案

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** 基于当前股票分析页已经实际返回的财报、五年健康度、最新季报 TTM、预警与行业数据，分阶段提升“发现问题—判断相对位置—形成跟踪清单”的能力，同时不把季度数据混入五年年度评分。

**Architecture:** 继续以 `/api/stock-score-report-history` 为“单股财报事实源”，页面端只做展示和可复核的轻计算；新增的横向/估值能力单独提供 API，避免把行业全量扫描塞进单股接口。所有新图表沿用当前柱图/色彩/TTM 标记契约：期间流量为 `26Q2(TTM)`，期末时点值为 `26Q2(非TTM)`。

**Tech Stack:** Python 标准库 HTTP handler、现有 `app/financial` 健康度与季度监测模块、现有 `app/relative_valuation` 与 `app/industry` 数据、原生 HTML/CSS/JavaScript、`unittest`。

---

## 0. 当前事实基线

当前单股接口已实际返回：

- `reports`：收入、归母/扣非利润、毛/净利率、扣非 ROE、经营现金流、自由现金流、CapEx、负债率、商誉、应收、库存、权益、总资产等。
- `health`：五个完整年报范围、六项健康度、评分/覆盖度、红旗、调查项、年度派生序列和审计证据。
- `quarterly_monitor`：最新期、TTM、同比、偏离值（gaps）、实时评分、维度状态、季度预警。
- `industry`：已随接口返回行业信息；项目内已有申万行业估值分位和成员样本能力（`app/industry/templates.py`、`app/relative_valuation/`）。

因此，优先实施不依赖新数据采集的功能；横向比较与估值联动应使用独立 API，避免增加当前单股接口的响应和缓存负担。

## 1. 功能候选与优先级

| 优先级 | 功能 | 用户问题 | 数据就绪度 | 工作量 | 主要风险 |
|---|---|---|---|---|---|
| P0 | 财报变化/异常摘要 | “最新季报相对年报，究竟哪里变坏或变好？” | 已就绪 | 小 | 不能把提示写成因果或投资建议 |
| P0 | TTM/年度/时点口径审计抽屉 | “这根柱怎么来的、为什么不能 TTM？” | 已就绪 | 小 | 信息过多影响主页面密度 |
| P0 | 财报事件时间线 | “何时披露、何时触发预警、变化发生在哪期？” | 基本就绪 | 中 | 历史预警需明确是当前规则回算还是当期快照 |
| P1 | 同行业财务位置卡 | “这个指标在申万二级行业中处于什么位置？” | 行业/估值就绪；财务横向需汇总 | 中 | 同行业财务报告期不齐，必须披露覆盖率 |
| P1 | 估值—业绩联动 | “低估值是否由盈利质量下降造成？” | 估值数据基础就绪 | 中 | 估值与财务报告时点不一致，不得暗示因果 |
| P1 | 自选股横向比较/财报筛选 | “我的股票里谁的质量改善、谁出现风险？” | 单股数据就绪；批量聚合待建 | 中至大 | 计算量、缓存、缺失数据与可比性 |
| P2 | 财报质量与数据可用性面板 | “哪个结论可用、哪个因数据缺失不能判断？” | 已就绪 | 小 | 与已有覆盖度/调查项重复，需整合而非堆叠 |
| P2 | 同行趋势/异常雷达 | “相对同行是改善还是恶化？” | 需构建行业历史面板 | 大 | 历史口径、幸存者偏差、行业结构差异 |

## 2. 推荐实施顺序

### 第一阶段（推荐先做）：财报变化与口径可审计性

优先做 P0-1 与 P0-2，原因是它们只使用现有单股接口，能立即提升页面解释力，不引入行业样本时点不齐的问题。

### 第二阶段：单股“事件化”阅读

做 P0-3，把当前散落在年度结论、季度预警、图表最新柱中的信息组织为可追溯时间线。

### 第三阶段：相对估值和行业位置

做 P1-1 与 P1-2，但必须先完成覆盖率、报告期和估值日期披露设计。

### 第四阶段：自选股批量决策

最后做 P1-3；它的价值高，但需要服务端批量缓存、排序与数据缺失策略，不能直接循环调用单股 API。

## 3. 第一阶段的具体方案

### 功能 A：最新财报变化摘要（P0）

**用户价值：** 在看图前先回答“最新一期最重要的三项改善/恶化是什么”，并能跳到对应图与证据。

**展示：** 在“年度与季度财报监测对比”下新增紧凑的“最新财报变化”区块，最多显示：

1. 经营表现：TTM 营收/扣非利润同比、毛利率/净利率变化；
2. 现金与投入：TTM 经营现金流、自由现金流、CapEx 强度；
3. 营运与风险：应收/库存相对营收的增速差、负债率、商誉变化；
4. 每项显示状态（改善/平稳/需关注/数据不足）、一句事实描述和“查看指标”锚点。

**口径：**

- 流量、利润率只使用 `quarterly_monitor.ttm` 与同比字段；显示 `26Q2(TTM)`。
- 应收、库存、负债率、商誉只使用最新期末值或期末同比差；显示 `26Q2(非TTM)`。
- 仅复用已有 `quarterly_monitor.dimensions`、`alerts`、`gaps` 和 `health` 证据，前端不自行推断红旗。

**Files:**
- Modify: `web/stock-analysis.html`
- Modify: `web/stock-analysis.js`
- Modify: `web/styles.css`（如公共样式无法覆盖）
- Test: `tests/test_stock_analysis_page.py`

**TDD/验收：**
1. 为“最多三类摘要、TTM/非 TTM 标签、数据不足态、跳转锚点”写失败测试。
2. 只新增 `renderLatestReportChanges(quarterlyMonitor, health)`，不重算后端指标。
3. 使用贵州茅台及一只季报不完整股票检查 API 和浏览器。
4. 验证年度区仍只使用五个完整年报，季度摘要不得改写年度得分。

### 功能 B：指标口径与数据血缘抽屉（P0）

**用户价值：** 点击指标名称或最新柱标签，即可看到“字段、公式、期别、报告日期、TTM 是否适用、缺失时为何不算”。

**展示：** 一个统一 dialog，不在图卡中常驻堆文字。内容分四行：

- 当前显示值与标签；
- 口径：TTM / 期末时点 / 年度；
- 计算式和所用报告期；
- 数据限制与不可比提示。

**实现原则：** 建立前端 `METRIC_DEFINITIONS` 配置（中文名称、指标类型、原始字段、TTM 公式/不适用原因、单位）；所有图卡从同一配置读取 title、标签、dialog 文案，避免业务解释复制在 HTML 中。

**Files:**
- Modify: `web/stock-analysis.js`
- Modify: `web/stock-analysis.html`
- Modify: `tests/test_stock_analysis_page.py`

**验收：** 对营收、扣非 ROE、应收账款、应收增速差四类代表指标逐项验证；其中后两项必须明确说明“期末时点/同比差，不适用 TTM”。

### 功能 C：财报事件时间线（P0）

**用户价值：** 将“报告日、季度预警、红旗、趋势变化”按时间排成一条线，减少用户在多张图卡之间来回对照。

**MVP 边界：** 只展示已有 `reports[].report_date`、最新 `quarterly_monitor.alerts`、当前五年年度红旗/调查项；历史事件标为“基于当前规则回看”，不能伪装成历史实时预警。

**后端建议：** 新增专用 `/api/stock-analysis-events`，返回稳定的 `{date, period, source, severity, title, detail, metric_refs, basis}` 事件数组。不要让前端遍历深层健康度对象拼装业务事实。

**Files:**
- Create: `app/financial/analysis_events.py`
- Modify: 对应 HTTP handler 注册文件（先定位当前 `/api/stock-score-report-history` handler）
- Modify: `web/stock-analysis.html`
- Modify: `web/stock-analysis.js`
- Test: `tests/test_financial_health.py`、`tests/test_stock_analysis_page.py`、新增 handler 测试。

**验收：** 时间排序、报告期显示、TTM/非 TTM 标签、空事件状态、当前规则回看披露，以及真实 API/browser 检查。

## 4. 第二阶段方案：行业位置与估值—业绩联动

### 功能 D：申万二级行业财务位置卡（P1）

**输出：** 对营收增长、扣非 ROE、FCF Margin、资产负债率、应收/库存增速差等指标显示：公司值、行业中位数、行业分位、样本量、可比报告期覆盖率。

**API 边界：** 新增 `/api/stock-financial-peer-summary?market=&symbol=&as_of_period=`，后端预聚合或有界缓存。返回每个指标的 `value`、`percentile`、`industry_median`、`n`、`coverage`、`period_alignment`。

**严格规则：**

- 同比或 TTM 指标仅与相同报告期/同一 `as_of_period` 样本比较；
- 财务风险类指标的“较低更好”只影响 UI 文案，不篡改原始分位；
- 样本不足/报告期不齐必须显示不可比，不补零；
- 金融/地产沿用现有“不适用”门控。

### 功能 E：估值—业绩联动卡（P1）

**输出：** 将已有行业估值分位与财务质量放在同一个卡中：估值分位、盈利质量状态、近期趋势、解释性提示（非因果）。

**关键文案：** “低估值与财务压力同时出现”只能描述共现，不得输出买卖建议；估值快照日期和财报期必须并排展示。

**复用：** `app/industry/templates.py` 的行业估值/成员样本能力、`app/relative_valuation` 的相对估值结果、当前 `health` 与 `quarterly_monitor`。

## 5. 第三阶段方案：自选股横向比较与筛选（P1）

**目标：** 在自选股中按“季度风险变化”“TTM 盈利质量改善”“年度健康度”“估值分位”排序，点击后进入单股页审计。

**架构：**

1. 新建批量服务，按交易日/财报更新日生成或缓存简明快照；
2. API 只返回用户自选范围，不返回全市场明细；
3. 单股页仍是事实审计页，横向页只提供排序和跳转；
4. 缺失季报/不适用行业独立分组，不与完整样本强行排名。

**首版筛选条件：**

- 五年年度健康度 ≥ 阈值且无高严重度年度红旗；
- 最新季度实时评分改善或无新增高严重度预警；
- TTM 扣非利润/FCF 为正；
- 应收与库存增速差未恶化；
- 可选叠加行业估值分位。

这不是买入信号；页面必须展示样本日期、覆盖率和各条件的未覆盖原因。

## 6. 统一数据质量与展示约束

1. 五年年度评分/证据/派生序列永远只用连续完整年报；最新季报只在季度监测、TTM 图和单独标识区域出现。
2. 不适用 TTM 的值必须标记 `26Q2(非TTM)`；不得显示裸 `26Q2`。
3. 财务横向比较必须同时展示样本数、对齐报告期、覆盖率和数据日期。
4. 缺失值显示“数据不足/不可比”，不得当作 0 或“正常”。
5. 年度红旗、季度预警、数据质量不足必须并列，不得让综合分掩盖红旗。
6. 任何估值和业绩联动只做事实/相对位置展示，不输出确定性交易建议。

## 7. 推荐首个可开发包

建议用户优先确认：**功能 A + 功能 B**。

理由：完全建立在当前单股 API 的真实数据上；能立即回答“本季发生了什么、口径是什么”；改动范围可控；也为事件时间线、行业比较、自选股横向筛选建立统一的指标定义与审计基础。

- 真实 API：普通工业股 + 季报缺失/行业不适用股票。

- 新增后端字段时验证完整链路：源数据 → handler JSON → 前端解析 → DOM。
